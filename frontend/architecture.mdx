## Architecture Overview

The OpenSource Together frontend follows a **feature-based architecture** that prioritizes modularity, maintainability, and scalability. This approach organizes code by business features rather than technical layers.

The application is built with **Next.js** using the App Router, **React**, and **TypeScript** for type safety. Development uses **Turbopack** for fast bundling and hot module replacement.

<Warning>
  **Critical**: All developers must follow the architectural principles outlined
  in this guide. Violations will cause maintenance issues and performance
  degradation.
</Warning>

## Core Architecture Principles

### 1. Feature-Based Organization

Each feature is an autonomous module under `src/features/` containing all related code:

```
src/features/
├── auth/
│   ├── components/     # Auth-specific UI components
│   ├── views/         # Auth pages and views
│   ├── forms/         # Login/register forms
│   ├── hooks/         # Auth business logic
│   ├── services/      # Auth API calls
│   ├── stores/        # Auth client state
│   ├── validations/   # Auth schemas (Zod)
│   └── types/         # Auth TypeScript types
├── projects/
│   ├── components/    # Project UI components
│   ├── views/         # Project pages
│   ├── forms/         # Project forms
│   ├── hooks/         # Project business logic
│   ├── services/      # Project API calls
│   ├── stores/        # Project client state
│   ├── validations/   # Project schemas
│   └── types/         # Project types
└── dashboard/
    └── ...           # Dashboard feature structure
```

## File Naming Conventions

All files follow strict naming conventions with precise suffixes:

| Suffix           | Purpose                    | Example                     |
| ---------------- | -------------------------- | --------------------------- |
| `.component.tsx` | UI components              | `ProjectCard.component.tsx` |
| `.view.tsx`      | Main pages/views           | `ProjectsList.view.tsx`     |
| `.form.tsx`      | React Hook Form components | `CreateProject.form.tsx`    |
| `.hook.ts`       | Business logic hooks       | `useProjects.hook.ts`       |
| `.service.ts`    | API calls/services         | `projects.service.ts`       |
| `.store.ts`      | Zustand stores             | `projects.store.ts`         |
| `.schema.ts`     | Zod schemas                | `project.schema.ts`         |
| `.type.ts`       | TypeScript types           | `project.type.ts`           |
| `.config.ts`     | Configuration              | `query.config.ts`           |

## State Management Patterns

### TanStack Query Configuration

The application uses **TanStack Query** for server state management. Configuration is typically done in the query client setup:

```typescript
// shared/lib/query-client.ts
import { QueryClient } from "@tanstack/react-query";

export const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 5 * 60 * 1000, // 5 minutes
      gcTime: 10 * 60 * 1000, // 10 minutes (formerly cacheTime)
      retry: 3,
      refetchOnWindowFocus: false,
    },
  },
});
```

<Info>
  **Note**: In TanStack Query v5, `cacheTime` has been renamed to `gcTime`
  (garbage collection time).
</Info>

### Zustand Store Pattern

```typescript
// features/projects/stores/projects.store.ts
interface ProjectsState {
  filters: ProjectFilters;
  selectedProject: Project | null;
  setFilters: (filters: ProjectFilters) => void;
  setSelectedProject: (project: Project | null) => void;
}

export const useProjectsStore = create<ProjectsState>((set) => ({
  filters: defaultFilters,
  selectedProject: null,
  setFilters: (filters) => set({ filters }),
  setSelectedProject: (project) => set({ selectedProject: project }),
}));
```

## Best Practices

### ✅ Do's

- Organize code by business features
- Use TypeScript for all code
- Validate API data with Zod schemas
- Keep components stateless and pure
- Use business logic hooks for state access
- Implement proper error boundaries
- Write unit tests for business logic

### ❌ Don'ts

- Put business logic in UI components
- Mix server and client state
- Duplicate data between stores
- Create circular dependencies between features
- Skip type definitions
- Ignore error handling

## Development Workflow

1. **Feature Development**: Create new features in `src/features/[feature-name]/`
2. **Component Creation**: Use `.component.tsx` suffix for UI components
3. **Business Logic**: Implement in `.hook.ts` files
4. **API Integration**: Use `.service.ts` for external calls
5. **State Management**: Use appropriate store (TanStack Query vs Zustand)
6. **Type Safety**: Define types in `.type.ts` files
7. **Validation**: Use Zod schemas in `.schema.ts` files
