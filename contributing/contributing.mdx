## The workflow

<Steps>
  <Step title="Fork and branch">
    Branch from `develop`, not `main`.

    ```bash
    git checkout develop
    git pull
    git checkout -b feat/your-feature
    ```

  </Step>
  <Step title="Make your change">
    Follow the [architecture guide](/web-app/architecture). Features live in
    `src/features/`, cross-feature code in `src/shared/`.
  </Step>
  <Step title="Run what CI runs">
    ```bash
    pnpm lint
    pnpm type-check
    pnpm test:mock
    pnpm build
    pnpm worker:build
    ```
  </Step>
  <Step title="Open a pull request against `develop`">
    Keep it small and purposeful. Include before/after screenshots for anything visual. Avoid
    unrelated formatting or refactors. They make review much harder.
  </Step>
</Steps>

### Branches

`develop` is the default branch. Pull requests target `develop`; `develop` is promoted to
`main` for releases.

Branch names follow `type/kebab-case-description`:

| Prefix | Used for |
| --- | --- |
| `feat/` | New features |
| `fix/` | Bug fixes |
| `refactor/` | Restructuring without behaviour change |
| `chore/` | Dependencies, config, tooling |
| `design/` | Visual and UI polish |

Branches tied to a tracker issue also appear as `ost-420-short-description`. Nothing enforces
either convention automatically. Match what's already there.

### Commits

[Conventional Commits](https://conventionalcommits.org/), lowercase, scope optional:

```
feat: add bookmark button to project cards
fix: prevent duplicate bookmark requests
refactor: extract pagination into a shared hook
chore(deps): update next to 15.5.23
```

The project also uses `design:` for UI polish and `doc:` (singular) for documentation. There's
no commitlint and no `commit-msg` hook, so this is convention rather than validation.

## What CI checks

Every push and pull request to `main` or `develop` runs the workflow in
`.github/workflows/ci.yml` on Node 22:

```bash
pnpm i --frozen-lockfile
pnpm lint          # Biome: lint, formatting, and import order
pnpm type-check    # tsc --noEmit
pnpm test:mock     # the mock API test suite
pnpm build         # next build
pnpm worker:build  # the Cloudflare Workers bundle
```

<Warning>
  `--frozen-lockfile` means a stale or hand-edited `pnpm-lock.yaml` fails the build
  immediately. If you touched `package.json`, commit the lockfile that `pnpm install`
  regenerated.
</Warning>

Two things people miss: `pnpm build` and `pnpm worker:build` are part of CI, so a change that
type-checks can still fail on a build-time error. Run all five before pushing.

### Your commit will be reformatted

A husky `pre-commit` hook runs Biome on staged files with `--write` and restages the result.
Your commit may therefore contain formatting you didn't type. That's expected. The commit
only fails if Biome finds something it can't fix automatically.

Hooks install themselves when you run `pnpm install`.

## Code standards

<AccordionGroup>
  <Accordion title="Formatting and linting: Biome, not ESLint/Prettier">
    The project uses **Biome** for linting, formatting, and import organization. Run
    `pnpm lint:write` to fix issues automatically.

    Settings that surprise people: 80-column lines, double quotes, ES5 trailing commas, and
    **TypeScript `enum` is banned** (`noEnum`). Use a union type or a `const` object instead.
    Tailwind classes are auto-sorted inside `cn`, `clsx`, and `cva`.

  </Accordion>
  <Accordion title="Structure">
    - Domain code belongs in its feature folder under `src/features/`.
    - Cross-feature components, hooks, utilities and types go in `src/shared/`.
    - Reuse existing design-system components and tokens before writing new styles.
    - Keep existing naming patterns, and keep mock-only files suffixed with `.mock`.

    Full details in the [architecture guide](/web-app/architecture).

  </Accordion>
  <Accordion title="Testing: be aware of what exists">
    There is **one** automated test file: `src/mocks/handlers.mock.test.ts`, 15 cases run with
    `node:test` via `pnpm test:mock`. It covers the mock API's behaviour and fixture
    invariants.

    There is no component, integration, end-to-end, or visual regression testing. Lint, types,
    and the two builds are the safety net, which is exactly why running all five checks
    matters, and why screenshots on visual PRs are genuinely useful to reviewers.

    If you change mock behaviour or seed data, add a focused test.

  </Accordion>
</AccordionGroup>

## Reporting a problem

Before opening an issue, check which layer it's in:

- The mock API logged an **unhandled route** and returned `501` → a local API flow is missing.
  Say which route in the issue, or [add the handler](/web-app/mock-api).
- Anything else → an app issue.

Include reproduction steps, what you expected, and screenshots or console output.
